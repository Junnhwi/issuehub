# 설계 결정 기록

### D1. create-next-app 대신 수동 구성 (2026-11-19)
루트에 설계서 파일이 이미 있어 create-next-app이 거부하거나 중첩 폴더를 만들 위험이 있었다. package.json과 설정 파일을 직접 작성했다.

### D2. 버전 선택
Next 16.4, React 19.3, Tailwind 4.3, zod 4, supabase-js 2, @anthropic-ai/sdk 1.10 (설치 시점 최신 안정). TypeScript는 7.x 대신 **5.9**, ESLint는 10 대신 **9** — Next/eslint-config-next와의 호환을 우선했다.

### D3. 데모 데이터는 DB에 쓰지 않는다
데모는 코드 내 고정 데이터(`demo-data.ts`)로 어댑터만 바꿔 제공한다. 실DB에 가짜 행이 섞일 위험을 없앤다. 제목 `[데모]`, 출처 `kind: "demo"`, 링크 example.com, completed 요약에는 "예시 텍스트·AI 생성 아님" 표시.

### D4. 필터·정렬·growth 규칙을 순수 함수로
데모 어댑터와 테스트가 같은 `query.ts`/`growth.ts`를 쓰고, Supabase는 같은 규칙의 SQL view(`repository_feed`)를 쓴다. 규칙을 바꾸면 두 곳을 함께 수정한다.

### D5. cursor = offset
여러 정렬(최신/인기/연관도/growth)을 하나의 방식으로 지원하려고 offset 기반 cursor를 썼다. 데이터가 수만 건 이상이 되면 keyset 페이지네이션으로 바꾼다.

### D6. 연관도 = 키워드 일치 수
“의미 없는 가짜 점수 금지”에 따라 설명 가능한 지표(등록 토픽 키워드 일치 수, 일치 없으면 null)만 쓴다. 인기 지표(HN points)는 `popularity`로 분리했다.

### D7. AI 요약은 별도 스크립트, 웹앱은 키를 갖지 않는다
웹앱(Vercel)에는 secret/Anthropic 키가 없다. 수집·요약은 GitHub Actions에서만. 요약 근거가 80자 미만이면 호출 없이 `skipped`. 모델 출력은 구조화 출력(zod) + 후처리 검증(문장 수 2~4, 개수·길이, 등록 토픽만, HTML 제거). 정책 거절 시 서버 측 fallback 사용.

### D8. 북마크는 localStorage
설계서 MVP 범위. `bookmarks` 테이블과 소유자 RLS는 마이그레이션에 미리 정의했지만 API는 만들지 않았다.

### D9. 다크 테마 기본 + 페인트 전 적용
`<html data-theme>`을 인라인 스크립트로 설정하고 색은 모두 CSS 변수 토큰. 라이트 accent `#0284C7`는 작은 텍스트에서 대비가 부족해 텍스트용 `--accent-fg: #0369A1`을 따로 두었다.

### D10. Data API 권한을 별도 마이그레이션으로 명시 (2026-11-19)
실제 Supabase 프로젝트에 0001을 적용했더니 secret key를 포함한 모든 요청이 `42501 permission denied`였다. 최근 프로젝트는 SQL로 만든 테이블에 API 역할 권한을 자동으로 주지 않는다. 이미 0001을 적용한 DB가 있으므로 0001을 고치지 않고 `0002_api_grants.sql`로 GRANT를 추가했다. 공개 역할(anon/authenticated)에는 SELECT만, 쓰기는 service_role(수집기)만.

### D11. 디자인 스킬은 taste-skill v1, 최신판 2.5는 보류 (2026-11-19)
2.5는 회사 홍보 사이트용으로 한 화면 한 섹션·사진·셰이더·Next.js 정적 export를 강제하고 매 턴 Stop 훅으로 자체 Node 검사기를 실행한다. 정적 export는 API 라우트와 동적 렌더링을 깨므로 IssueHub에 맞지 않는다. 스크립트·훅이 없는 v1(SKILL.md 한 파일)을 커밋 5e08c93 기준으로 고정 설치하고(해시 검증), 다이얼을 대시보드용(3/3/7)으로 적용했다. 설계서와 충돌하는 규칙(Phosphor 아이콘, 상시 무한 애니메이션)은 설계서를 따른다.

### D12. 저장소 한국어 요약은 상태 컬럼 없이 summary_ko로 관리 (2026-11-19)
마이그레이션을 늘리지 않으려고 `summary_ko`의 null(미처리)/""(근거 부족·영구 실패)/문자열(완료)로 구분한다. 일시 오류는 null로 남겨 다음 배치에서 재시도한다. 화면·API에는 ""를 null로 바꿔 내보낸다.

### D13. 토픽 색 점과 원문 링크 노출 (2026-11-19)
토픽을 한눈에 구분하도록 토픽마다 색 점을 두고(`src/config/topics.ts`의 `color`), 칩·사이드바·필터에서 같은 색을 쓴다. 색은 점에만 쓰고 이름을 항상 함께 표시한다(색에만 의존하지 않음, 보라색 제외). 각 이슈 행에는 "원문 · 호스트 ↗" 버튼을 항상 보이게 두고, Hacker News 글은 `source_item_id`로 만든 HN 토론 링크를 함께 둔다. 원문과 토론 URL이 같으면(텍스트 글) 토론 링크는 숨긴다.

### D14. 무료 번역·요약: Gemini 무료 티어 + 배치 처리 (2026-11-19)
무료 대안 중 GitHub Models는 2026-07-30 종료되어 제외했다. Google Gemini는 공식 가격표에 무료 티어(gemini-3.5-flash-lite 등)가 있어 기본 제공자로 삼고, Anthropic은 선택지로 남겼다(`src/lib/ai/provider.ts`, `AI_PROVIDER`). 무료 한도를 아끼려고 기사 8건을 요청 1번에 묶고 요청 사이를 4.5초 띄운다. 제목·발췌 번역은 요약과 분리해 저장한다(`excerpt_ko`, 0003 마이그레이션): 근거가 부족한 글도 번역은 보여 주되 요약은 만들지 않는다. 무료 티어 입력은 Google 제품 개선에 쓰일 수 있으나 보내는 것은 공개 기사 메타데이터뿐이다.

### D15. 수집 주기 1시간, Actions v7 (2026-11-19)
새 글을 더 빨리 보여 주려고 cron을 6시간에서 매시 정각(`0 * * * *`)으로 줄였다. GitHub는 정각 예약이 몰려 수 분~수십 분 늦게 시작될 수 있다. 실행이 겹치면 `concurrency`가 순서대로 대기시킨다. 번역·요약은 이번 달 처리 건수 상한(`AI_MONTHLY_REQUEST_CAP`, 기본 3000)이 그대로 막아 주고, 1회 최대 40건이라 Gemini 무료 한도 안에 든다. Node 20 지원 종료 경고를 없애려고 `actions/checkout`·`actions/setup-node`를 v7(Node 24 런타임)로 올렸다.

### D16. 화제도는 공개 수치의 구간만, 노션은 Markdown 복사로 (2026-11-20)
"얼마나 이슈가 됐나"를 보여 주되 D6(가짜 점수 금지)를 지키려고, 출처가 공개한 숫자(HN 점수·댓글 수)를 그대로 보여 주고 고정 기준으로만 구간을 나눈다(`src/lib/buzz.ts`: 300점/150댓글 이상 큰 화제, 100점/50댓글 이상 화제). 기준은 칩 툴팁과 About에 공개한다. 공식 블로그(RSS)는 조회수·평가를 공개하지 않으므로 비워 둔다. HN 댓글 수는 `descendants`를 `comments_count`(0004)에 저장한다. 노션 연동은 API 키·쓰기 권한 없이 쓰도록 "노션용 복사"(Markdown 노트 초안)로 시작했다. 노션은 붙여 넣을 때 제목·목록·인용을 블록으로 바꾼다.

### D17. 수집 예약은 매시 41분 (2026-11-20)
정각(`0 * * * *`)으로 바꾼 뒤 14번 중 1번만 예약 실행됐다(이전 6시간·17분 설정도 1번 중 0번). GitHub 문서는 매시 정각을 고부하 시간으로 꼽고 이때 예약 실행이 늦어지거나 버려질 수 있다고 한다. 어느 분이든 보장은 없으므로(2026년 커뮤니티 보고: 정각이 아닌 시각도 수 시간 지연) 덜 붐빌 가능성이 큰 시각을 골랐다: 정각과 5분 단위(사람들이 흔히 쓰는 값), 블로그에서 흔히 권장하는 17·23·37분을 피한 41분. 간격은 1시간을 유지한다. 한 번 건너뛰어도 다음 실행이 이어서 모으므로, 간격이 짧을수록 공백이 짧다. 그래도 자주 빠지면 외부 스케줄러(예: Supabase pg_cron)가 `workflow_dispatch`를 호출하는 방식으로 바꾼다.

### D18. 정시 수집은 Supabase pg_cron이 workflow_dispatch로 요청 (2026-11-20)
41분 예약도 첫 두 회차(03:41, 04:41 UTC)가 실행되지 않았다. 워크플로는 active였고 GitHub 장애 공지도 없었다. 즉 이 저장소에서는 GitHub `schedule`을 믿을 수 없다. 수집 코드(Node)는 그대로 Actions에서 돌리고, 시계만 Supabase pg_cron으로 옮겼다: 매시 20분에 pg_net이 GitHub REST API로 `workflow_dispatch`를 보낸다(0005). 토큰은 Fine-grained PAT(issuehub 저장소, Actions 쓰기만)를 Supabase Vault에 두고 저장소에는 커밋하지 않는다. 두 실행이 겹쳐도 `concurrency`로 순서대로 돌고 upsert·pending 처리라 중복 저장·중복 요약이 없으므로 GitHub 예약(41분)은 예비로 남긴다.

### D19. Steam 게임 동향은 공개 API만, 평가는 Steam 값 그대로 (2026-11-20)
"어떤 게임이 만들어지고 유행하는지"를 보려고 Steam 목록 4개(동시접속 상위, 최고 인기, 신규 출시, 곧 출시)를 매 수집마다 가져온다. 키가 필요 없는 공개 엔드포인트만 쓴다: 상점 `featuredcategories`, `ISteamChartsService/GetMostPlayedGames`, 상세는 `IStoreBrowseService/GetItems`로 50개씩 한 번에(한국어 소개·평가 요약·태그·가격·이미지), 현재 동시접속은 `GetNumberOfCurrentPlayers`. 상점의 `appreviews` JSON은 현재 상점 첫 화면으로 리다이렉트되어 쓰지 않았다. 평가는 Steam 표기("매우 긍정적")·긍정 비율·평가 수를 그대로 보여 주고 자체 점수를 만들지 않는다. 출시일은 Steam 상점과 같은 미국 태평양 시간 기준 날짜로 표기한다. 목록 순위는 `games.ranks`(jsonb)에 마지막 수집 기준으로 저장하고, 이번 수집에 없는 게임은 순위를 비워 화면에서 빠지게 한다(행은 남김). 판매 순위·인기 신작·인기 출시 예정은 상점 검색 JSON(`search/results?filter=topsellers|popularnew|popularcomingsoon&json=1`, appid는 이미지 URL에서 추출)을 쓴다. 기본 `featuredcategories` 목록은 10개 안팎이고 "곧 출시"가 다음 날 나오는 작은 게임 위주라 "주목받는 게임"에 맞지 않았다. 검색 JSON을 못 받으면 featuredcategories로 대신한다. 한국어 소개가 없는 게임만 요약 단계에서 AI로 번역한다(`description_ko` null=대기, ''=설명 없음).

### D20. Steam 가격 추이는 IsThereAnyDeal API, 그래프는 서버 렌더 SVG (2026-11-20)
Steam은 가격 이력 API가 없다. SteamDB는 공개 API가 없고 한국 지역을 추적하지 않는다. IsThereAnyDeal(ITAD)는 `/service/shops/v1?country=KR`에서 Steam(id 61)을 33만여 게임으로 추적하고, `/games/history/v2`(country=KR, shops=61, since)로 변경 기록(시각·가격·정가·할인율·통화)을 준다. appid→ITAD id 조회는 키가 필요 없고, 이력은 무료 API 키가 필요하다(키 없이 403). 한도는 5분에 1000회(429 + Retry-After)라 1회 40개, 게임마다 12시간에 한 번만 갱신하고 두 번째부터는 마지막 기록 이후만 받는다. 약관: 공개 앱 상업 이용 가능, 출처 표기 권장, 제공 데이터 변경 금지, 경쟁 서비스 금지 → 값은 그대로 저장·표시하고 Steam 한 상점만 보여 주며 상점 비교·특가 알림은 만들지 않는다. 세일 기간은 할인율>0 기록부터 다음 기록까지로 계산하고, 진행 중인 세일의 종료일은 Steam GetItems의 `discount_end_date`를 쓴다. 그래프는 계단형(가격은 바뀐 시점부터 유지)이고, 클라이언트 컴포넌트를 늘리지 않으려고 서버에서 SVG로 그린다. 호버는 SVG `<title>`(마우스를 올리면 날짜·가격), 같은 내용을 표(세일 기록)로도 제공한다.

### D21. 인기 신작은 출시 6개월 이내만, 가격 그래프는 가로 스크롤 (2026-11-20)
Steam '인기 신규 출시'에는 대형 업데이트로 다시 올라온 오래된 게임(예: 2017년 PUBG)이 섞인다. 상위 100개를 받아 출시일이 최근 183일 안인 게임만 남기고 순위를 1부터 다시 매긴다(`keepRecentReleases`, 출시일 모름은 제외). 가격 그래프는 기간 전체를 한 화면에 넣으니 2주 세일 띠가 몇 px로 뭉개져, 하루 2.6px 고정 폭으로 넓게 그리고 가로 스크롤(막대 + 그래프 위 마우스 휠)로 이동한다. 처음에는 최신(오른쪽 끝)을 보여 주고, 가격 축은 왼쪽에 고정한다. 휠을 가로 이동으로 바꾸려면 non-passive wheel 리스너가 필요해 작은 클라이언트 컴포넌트(`chart-scroller`) 하나를 추가했다. 양 끝에 닿으면 페이지 스크롤로 넘긴다.

### D22. 수집기의 외부 URL 요청은 SSRF 방어를 거친다 (2026-11-22)
HN 글 링크는 누구나 올릴 수 있는 임의 URL인데, 메타 설명을 읽으려고 `fetch(redirect: "follow")`로 그대로 요청하고 있었다. 수집기는 GitHub Actions 러너에서 돌기 때문에 클라우드 메타데이터 주소(169.254.169.254)나 내부 주소로 요청이 갈 수 있었다. `scripts/lib/safe-fetch.ts`로 바꿨다: http/https·기본 포트만, 자격 증명이 든 URL 거부, IP 표기(10진·16진·IPv4-mapped IPv6) 정규화 후 사설·루프백·링크 로컬·예약 대역과 IPv6 비전역 대역(6to4·Teredo 포함) 차단, 리다이렉트는 직접 따라가며 매번 재검사(최대 3회), 연결 시점의 DNS lookup에서 주소를 검사해 검사 후 다른 IP로 바뀌는 DNS rebinding도 막는다. 64KB·6초·Content-Type(text/html) 제한. RSS는 등록된 공식 피드만 쓰지만 응답 크기 상한(5MB)을 뒀다. `ingest.yml`의 수동 입력값은 셸에 직접 끼워 넣던 것을 환경 변수 + slug 형식 검사로 바꿨다.

### D23. 토픽은 강한 단어·제목 전용 단어·범용 단어로 나눠 점수로 태깅 (2026-11-22)
`agent`, `database`, `game`, `ai`, `browser` 하나만 걸려도 태깅되어 "FBI agent", "FBI database hacked", "UN autonomous weapons" 같은 글이 MCP·Backend 토픽으로 들어왔다. 강한 단어(제목 3·본문 2점), 제목 전용 단어(`ai`, `inference`: 제목 2점), 범용 단어(제목 1·본문 0.5점)로 나누고 2점 이상만 태깅한다. 실제 수집 글 191건에 돌려 보니 23건이 태그 없음이 되었는데 거의 모두 개발 주제가 아닌 글이었다. HN은 태그가 없는 글을 버리므로 후보 4배수 안에서 더 개발에 가까운 글이 채워진다. AI 분류는 비용·지연 대비 이득이 작아 넣지 않았다.

### D24. 기사 성격과 같은 사건 묶기는 렌더 시점 규칙으로 (2026-11-22)
기사 성격(발표·도구·튜토리얼·보안·연구·뉴스)은 제목·URL 규칙으로 화면에서 계산하고 DB에 저장하지 않는다(마이그레이션 없이 규칙을 고칠 수 있음). 기본값(뉴스·의견)은 표시하지 않아 배지가 늘지 않게 했다. 같은 사건 묶기도 홈 목록에서만 렌더 시점에 한다: 다른 도메인 + 72시간 이내 + 숫자·버전·CVE 토큰 일치 + 제목 단어 Jaccard ≥ 0.5. 실데이터에서 "FBI 데이터베이스 해킹" 3건이 묶였고, Next.js 16.2/16.3·서로 다른 CVE 같은 오탐은 없었다. 기사는 지우지 않고 대표 글 아래에 다른 출처 링크로 남긴다. Discover는 서버 페이지네이션이라 페이지마다 묶음이 달라져 적용하지 않았다.

### D25. AI 요약은 원문 대조를 통과해야 저장, HN은 발견 경로로만 표시 (2026-11-22)
기존 검증은 형식(문장 수·길이)뿐인데 홈에 "검증을 통과한 AI 요약"이라고 써 사실 검증처럼 읽혔다. 저장 전 자동 대조를 추가했다: 요약의 숫자가 제목·발췌·게시일에 있는지(영어 숫자 단어·월 이름 허용, "2가지" 같은 목록 세기는 제외), 원문의 보도·주장 표현(reportedly, claims, allegedly…)이 요약에 남았는지, 제목 번역에서 버전·연도·CVE가 바뀌지 않았는지, may·could·질문형 같은 불확실성이 사라지지 않았는지. 기존 요약 137건에 돌려 보니 연도 누락, "Alleged" 누락 같은 실제 오류가 잡혔다. 발췌 충분성은 길이 대신 정보량(서로 다른 단어 10개, 제목에 없는 단어 6개, 사이트 공통 문구 제외)으로 본다. 활용 예시는 "활용 아이디어 · AI 제안"으로 분리 표기한다. 이 확인은 원문 대조일 뿐 팩트체크가 아니라고 화면에 밝힌다. 모델·프롬프트 버전은 0008 열에 기록하며, 열이 없으면 기록만 건너뛴다. HN 글은 실제 발행처(원문 도메인)를 보여 주고 HN은 "HN에서 발견"으로 표시한다. HN 점수는 관심도일 뿐 사실 여부와 무관하다고 툴팁에 적었다.

### D26. 홈은 콘텐츠 우선, 운영 지표는 About으로 (2026-11-22)
홈 상단의 수집 기사 수·저장소 수·요약 완료 수 띠와 "최근 수집 출처"는 운영 정보라 About의 "데이터 소스" 섹션으로 옮겼다. 홈에는 수집 상태 한 줄만 남긴다. 순서는 화제의 이슈 → 최근 주목받는 GitHub 저장소 → 최신 이슈, 보조 영역에 Steam·토픽. 화제의 이슈에 나온 글은 최신 이슈에서 빼 중복 노출을 줄였다. 모바일 하단 탭은 6개에서 5개로(Topics는 각 목록의 토픽 필터·전체 메뉴와 겹침) 줄이고 글자를 12px로 키웠다. Star 증가 배지는 실제 관측 기간을 "N일"로 보여 준다(3일치를 7일 증가량이라 부르지 않음).

### D27. 연속 세일 병합, "역대 최저가" 대신 "기록상 최저가" (2026-11-22)
할인 중 할인율만 바뀐 기록(-30% → -50%)이 세일 2회로 세어졌다(실데이터 60개 게임 중 2개). 할인이 이어지는 동안의 기록은 한 세일로 합치고 할인율 범위·최저 세일가를 보여 준다. KR 기록은 2024년 12월부터라 "역대 최저가"는 과장이므로 "기록상 최저가"로 바꾸고 기록 시작일을 함께 표시한다. 현재 가격·세일 종료 예정일은 Steam 상점 값, 과거 기록은 ITAD 값임을 문구로 구분했다. 터치로 점을 눌러 가격을 보는 기능은 클라이언트 코드가 늘어 넣지 않고, 같은 내용을 아래 표에서 보도록 안내한다.

### D28. AI 원문 해설은 방문자 요청이 아니라 수집 배치에서 미리 만든다 (2026-11-22)
발췌 기반 요약은 짧고 두루뭉술해 공부용으로 부족했다. 원문 본문을 읽고 핵심 개념·주요 내용·적용 방법·근거 인용을 담은 학습용 해설을 만든다. 버튼을 누르면 그때 만드는 방식은 공개 엔드포인트가 AI 호출·DB 쓰기를 일으켜 "공개 쓰기 API 금지" 원칙과 무료 한도 남용 위험에 걸려, 매시 수집 뒤(`scripts/deep-read.ts`) 최근 3일 기사를 화제순으로 6건씩 미리 만든다(하루 약 144건, 하루 수집량보다 많음). 상세 페이지는 결과만 읽는다. 원문은 robots.txt에서 우리 수집기나 대표 AI 수집기(GPTBot·ClaudeBot·Google-Extended·CCBot 등)를 막았거나 `noai` 메타가 있으면 읽지 않는다(실측: Reuters·Guardian 거부). 본문은 AI 입력으로만 쓰고 저장하지 않으며, 해설과 원문에 그대로 있는지 확인한 짧은 인용(최대 3개)만 저장한다. 요청은 safe-fetch로만 한다(1.5MB·12초). 검증: 개요·본문·적용의 숫자는 원문과 대조하고, 인용은 원문에 없으면 뺀다. 용어 풀이는 일반 설명이라 대조에서 제외하고, 화면에 그렇다고 밝힌다. robots 거부·본문 부족은 skipped(재시도 안 함), 읽기 실패·검증 실패는 failed(최대 3회). 실측: Gemini 3.5 flash-lite 한 건 약 5초, nginx RCE 글의 CVE 두 개와 완화 설정을 정확히 설명했다.

### D29. 저장소는 README로 활용 가이드, 저장소 상세 페이지 추가 (2026-11-22)
저장소 설명 한 줄 요약만으로는 무엇에 쓰는지 알기 어려웠다. 공식 GitHub API(`/repos/{owner}/{repo}/readme`, Actions 토큰으로 시간당 5000회)로 README를 받아 배지·이미지를 빼고 AI가 무엇인지·제작자가 풀려는 문제·대상·주요 기능·활용 시나리오·시작하기·스택·한계를 정리한다. 명령어는 README에 한 글자도 다르지 않게 있을 때만 남긴다. 저장소 카드는 GitHub 대신 새 상세 페이지(`/github/[id]`)로 이동하고, GitHub 링크는 따로 둔다. 상세에는 관측 Star 추이(서버 SVG)를 함께 보여 준다.

### D30. '큰 화제'는 빨강 대신 파랑→보라, 모션은 CSS만 (2026-11-22)
빨강은 하락·경고로 읽혀 화제도에 맞지 않았다. 강조색 `--hot`(보라)을 추가하고 '큰 화제'를 파랑→보라 그라데이션 칩으로 바꿨다(빛이 천천히 지나감). 동적인 느낌은 의존성 없이 CSS로만 냈다. 목록 순차 등장(`.stagger`, nth-child 지연), 페이지 전환 페이드(`(site)/template.tsx`), 카드 호버 들림(`.lift`), 홈 배너의 흐르는 빛 번짐과 점 격자(`.banner`), 수집 상태 파동 점(`.live-dot`), 스켈레톤 빛 지나감을 넣었다. 모두 transform·opacity만 써서 레이아웃 비용이 없고, `prefers-reduced-motion`이면 멈춘다. framer-motion은 번들이 늘어 쓰지 않았다. 이미지는 GitHub 프로필(작게, 지연 로드)·Steam 썸네일·해설이 있는 글의 og:image만 쓰고 모두 lazy다. 라우트별 스켈레톤(홈·목록·상세·게임)을 실제 레이아웃과 같은 모양으로 맞췄다.
